#### NAT 동작 방식
다음 그림은 NAT 동작 방식을 알아보기 위한 예시이다.

<img width="628" height="472" alt="image" src="https://github.com/user-attachments/assets/2a5ccbfd-fb66-4741-9335-542dbe84351d" />

사용자(10.10.10.10)가 목적지 웹 서버(20.20.20.20)으로 통신하는 과정이다.
1. 사용자는 웹 서버에 접근하기 위해 출발지 IP를 10.10.10.10으로, 목적지 IP와 서비스 포트는 20.20.20.20과 80으로 패킷을 전송한다. 출발지 포트는 임의의 포트로 할당된다. 여기서는 2000번 포트로 가정한다.
2. NAT 역할을 수행하는 장비에서는 사용자가 보낸 패킷을 수신한 후 NAT 정책에 따라 외부 네트워크와 통신이 가능한 공인 IP인 11.11.11.11로 IP 주소를 변경한다. NAT 장비에서 변경 전후의 IP 주소는 NAT 테이블에 저장된다.
3. NAT 장비에서는 출발지 주소를 11.11.11.11로 변경해 목적지 웹 서버로 전송한다.
4. 패킷을 수신한 웹 서버는 사용자에게 응답을 보낸다. 응답이므로 수신한 내용과 반대로 출발지는 웹 서버(20.20.20.20)가 되고 목적는 NAT 장비에 의해 변환된 공인 IP(11.11.11.11)로 사용자에게 전송한다.
5. 웹 서버로부터 응답 패킷을 수신한 NAT 장비는 자신의 NAT 테이블에서 목적지 IP에 대한 원래 패킷을 발생시킨 출발지 IP 주소 10.10.10.10을 확인한다.
6. NAT 변환 테이블에서 확인된 원래 패킷 출발지 IP로 변경해 사용자에게 전송하면 최종적으로 사용자가 패킷을 수신한다.

#### PAT 동작 방식

<img width="635" height="476" alt="image" src="https://github.com/user-attachments/assets/e83cfec1-c9f9-424f-bafc-646bb2f33ed2" />

1. NAT의 1번 과정과 동일하다
2. NAT 장비는 사용자가 보낸 패킷을 받아 공인 IP인 11.11.11.11로 변경한다. 다만 출발지에 있는 다수의 사용자가 동일한 공인 IP로 변경되어야 하므로 패킷의 주소 변경 시 출발지 IP 뿐만 아니라 출발지의 서비스 포트도 변경된다.
출발지 IP와 출발지 서비스 포트는 NAT 장비에 의해 모두 변경되고 NAT 장비가 이 변경 정보를 NAT 테이블에 기록한다.
3. NAT 장비에서 변경된 출발지 IP 주소인 11.11.11.11과 서비스 포트 3000으로 패킷을 재작성해 웹 서버로 전송한다.
4. 패킷을 수신한 웹 서버는 출발지 IP는 서버의 IP인 20.20.20.20, 목적지는 11.11.11.11과 서비스 포트로 채워져 전송한다.
5. 응답 패킷을 수신한 NAT 장비는 NAT 테이블을 확인해 웹 서버로부터 받은 패킷의 목적지 IP 주소인 11.11.11.11이 원래 10.10.10.10.이며, 서비스 포트 3000이 원래 2000인 것을 확인한다.
6. NAT 장비는 NAT 테이블에서 확인한 목적지 IP 주소와 서비스 포트로 패킷을 재작성한 후 사용자에게 전달한다. 사용자는 NAT 장비에서 역변환된 패킷을 받아 웹 페이지를 표시한다.

만약 다른 IP를 가진 사용자가 동일하게 20.20.20.20 서버로 요청하는 경우, NAT 장비에서는 출발지 IP만 11.11.11.11로 동일하게 변경되고 서비스 포트는 다른 포트로 변경한다.
즉, PAT 동작 방식은 NAT과 거의 동일하게 이루어지지만 IP 주소 뿐만 아니라 서비스 포트까지 함께 변경해 NAT 테이블을 관리하므로 하나의 IP만으로도 다양한 포트 번호를 사용해 사용자를 구분할 수 있다. 서비스 포트의 개수는 제한되어 있어 재사용된다.

PAT은 다수의 IP가 있는 출발지에서 목적지 갈 때 NAT 테이블이 생성되므로, 응답에 대해 NAT 테이블을 참조할 수 있지만
PAT IP가 목적지일 때는 해당 IP가 어느 IP에 바인딩되는지 확인할 수 있는 NAT 테이블이 없으므로 사용할 수 없다.

#### SNAT과 DNAT
NAT을 사용해 네트워크 주소를 변경할 때 어떤 IP 주소를 변환하는지에 따라 두 가지로 구분한다.
- SNAT(Source NAT): 패킷의 출발지 주소를 변경하는 NAT
- DNAT(Destination NAT): 패킷의 목적지 주소를 변경하는 NAT

<img width="656" height="258" alt="image" src="https://github.com/user-attachments/assets/6c4e18a9-ede7-4d85-abbe-880235309263" />

어떤 주소를 변경해야 하는지는 서비스 흐름과 목적에 따라 결정된다.
서버에 요청 시 SNAT을 해 목적지로 전송하면 해당 트래픽에 대한 응답을 받을 때는 출발지와 목적지가 반대가 되므로 DNAT이 되는데, 이 때 트래픽을 요청하는 시작 지점만 고려해 SNAT 설정을 해야한다. NAT 장비를 요청이 처음 통과할 때 NAT 테이블이 생성되므로 응탑 패킷이 NAT 장비에 들어오면 별도의 NAT 설정 없이도 NAT 테이블을 사용해 반대로 패킷을 변환 해줄 수 있기 때문이다.
이 과정을 역 NAT이라고 하며, NAT이 정상적으로 수행되려면 역 NAT 과정이 함께 수행되어야 한다.

이제 SNAT과 DNAT의 몇 가지 사용 경우를 알아보겠다.
SNAT은 사설에서 공인으로 통신할 때 많이 사용된다. 그래야 해당 요청을 받은 목적지에서 다시 응답할 수 있는 경로를 찾을 수 있기 때문이다. 이것은 공유기처럼 PAT을 사용하는 경우에 해당할 수 있다.

다른 경우는 보안상 SNAT을 사용할 때이다. 회사에서 다른 대외사와 통신 시 별도의 다른 IP로 전환해 전송함으로써 내부 IP 주소를 숨길 수 있기 떄문이다. 보안상의 문제 뿐만 아니라 대외사와 통신해야 하는 사내 IP가 대외사의 사내 IP 대역과 중복될 때도 SNAT을 통해 중복 문제를 피할 수 있다. 이 경우에는 변경되는 IP가 반드시 공인일 필요는 없다.

로드 밸런서의 구성에 따라 SNAT을 사용하기도 한다. 이에 대해서는 12장에서 자세히 다루므로 넘어간다.

다음은 DNAT이다.
DNAT은 로드 밸런서에서 많이 사용한다. 사용자가 서비스 요청 시 로드 밸런서에 설정된 VIP(Virtual IP)로 서비스를 요청하고 로드 밸런서에서는 로드 밸런싱 될 서버의 Real IP로 DNAT해 내보낸다.

사내가 아닌 대외망과의 네트워크 구성에도 DNAT을 사용한다. 대외망과의 연동에서는 IP가 중복 될 수 있기도 하고, IP 주소가 제각각이므로 개별 라우팅을 설정하기 번거롭기 때문이다.


#### 동적 NAT과 정적 NAT
출발지와 목적지의 IP를 미리 매핑해 고정해놓은 NAT을 정적 NAT이라고 한다. 반대로 출발지나 목적지 어느 경우든 사전에 정해지지 않고 NAT을 수행할 때 IP를 동적으로 변경하는 것을 동적 NAT이라고 한다.

동적 NAT은 다수의 IP 풀에서 출발지와 목적지 IP가 정해지므로 최소한 출발지나 목적지 중 한 곳이 다수의 IP로 구성된 IP 풀이나 레인지(Range)로 설정되어 있다.
NAT이 필요할 때 IP 풀에서 어떤 IP로 매핑될 것인지 판단해 NAT을 수행하는 시점에 NAT 테이블을 만들어 관리한다. NAT 테이블은 설정된 시간동안 유지되고 시간이 지나면 사라지므로(NAT 테이블 타임아웃) 동적 NAT 설정은 서비스 흐름을 고려해 적용해야 한다.

정적 NAT은 출발지와 목적지 매핑 관계가 특정 IP로 사전에 정의된 것이므로 1:1 NAT이라고 부르기도 한다.

#### DNS

네트워크 프로토콜은 크게 두 가지로 나눌 수 있다. 실제로 데이터를 실어 나르는 데이터 프로토콜과, 데이터 프로토콜이 잘 동작하도록 도와주는 컨트롤 프로토콜이다.
컨트롤 프로토콜은 통신에 직접 관여하지 않지만 처음 통신 관계를 맺거나 유지하는 데 큰 역할을 한다. TCP/IP 프로토콜 체계를 유지하기 위한 주요 컨트롤 프로토콜에는 ARP, ICMP, DNS가 있다. 이 중 DNS(Domain Name System)는 도메인 주소를 IP 주소로 변환하는 역할을 한다.
IP 주소보다 도메인 주소를 이용하는 것이 사용자에게 더 익숙하고 서버 IP 변경에 쉽게 대처할 수 있으므로 네트워크 통신에서 DNS의 역할이 매우 중요하다.

최근 클라우드 기반 인프라 구성이 많아지면서 인프라가 빈번히 변경되어 DNS 설계가 더 중요해지고 있다.
또한 MSA(Micro Service Architecture) 기반의 서비스 설계가 많ㅎ아지면 다수의 API를 이용하다보니 사용자의 호출 뿐만 아니라 서비스 간 API 호출이나 인터페이스가 많아져 DNS의 역할이 더 중요해졌다.

#### DNS 소개
인터넷을 사용할 때 브라우저에 주소를 직접 입력하는 경우가 거의 없지만, 실제로는 우리 모르게 사용하는 링크들 조차 접속 주소가 지정되어 있다.
물론 서비스를 도메인 주소로 사용하더라도 실제로 패킷을 만들어 통신하려면 3계층 IP 주소를 알아야 하고 이를 위해 문자열로 이루어진 도메인 주소를 실제 통신에 필요한 IP 주소로 변환하는 DNS 정보를 네트워크 설정 정보에 입력해야 한다.

<img width="534" height="582" alt="image" src="https://github.com/user-attachments/assets/2f69e4dd-5151-4c26-b094-b24fba9f51eb" />

사용자가 도메인 주소를 사용하여 서비스를 욫청하면 네트워크 설정에 입력된 DNS로 해당 도메인에 대한 IP 주소 질의를 보내고 그 결괏값으로 요청한 도메인의 서비스 IP 주소를 받게 된다.

<img width="480" height="318" alt="image" src="https://github.com/user-attachments/assets/2a497937-6031-4a02-96f0-b581d5700792" />

사용자가 서비스를 찾아갈 때 뿐만 아니라 내부 시스템의 서비스 간 연결에도 DNS를 사용한다.
대부분 시스템 간의 연결은 복잡하므로, IP로 서비스 간 연결을 구성하면 어느 한 서비스의 IP 변경이 필요한 경우 여러가지 설정을 변경하거나 프로그램을 재배포해야 하기 떄문이다. 보통 인터넷 연결을 위한 DNS와 내부 서비스 간 통신을 위해 외부와 내부 DNS를 분리해 운영한다.

#### DNS 구조와 명명 규칙
도메인은 계층 구조로 되어있어 원하는 주소를 효율적으로 찾아갈 수 있다.
역트리 구조로 최상위 루트부터 Top-Level 도메인, Second-Level 도메인, Third-Level 도메인과 같이 하위 레벨로 원하는 주소를 단계적으로 찾아간다. 우리가 도메인 주소를 사용할 때는 각 계층의 경계를 "."으로 표시하고 뒤에서 앞으로 해석한다.

<img width="586" height="248" alt="image" src="https://github.com/user-attachments/assets/86b4d5c9-bb05-434a-81f5-136424600dd8" />

도메인 계층은 최대 128계층까지 구성할 수 있다. 계층별 길이는 최대 63바이트까지 사용할 수 있고 도메인 계층을 구분하는 구분자 "."를 포함한 전체 도메인 네임의 길이는 최대 255바이트까지 사용할 수 있다. 문자는 알파벳, 숫자, 대쉬("-")만 사용할 수 있고 대소문자 구분이 없다.

#### 루트 도메인
루트 도메인은 앞서 말했듯 도메인 트리의 최상위 영역이다. DNS 서버는 사용자가 쿼리한 도메인에 대한 값을 직접 갖고 있거나 캐싱된 정보를 이용해 응답한다. 만약 NDㄴ 서버에 해당 도메인의 정보가 없으면 루트 도메인을 관리하는 루트 DNS에 쿼리하게 된다.

루트 DNS는 전 세계에 13개가 있고 DNS 서버를 설치하면 루트 DNS의 IP 주소를 기록한 힌트(Hint) 파일을 갖고 있어 루트 DNS 관련 정보를 별도로 설정할 필요가 없다.

#### Top-Level Domain (TLD)
최상위 도메인인 TLD는 IANA(Internet Assigned Numbers Authority)에서 구분한 6가지 유형으로 구분할 수 있다.
각 유형은 다음과 ㄱ같으며 전체 리스트는 IANA 사이트에서 확인할 수 있다.
- Generic(gTLD)
- country-code(ccTLD)
- sponsored(sTLD)
- infrastructure
- generic-restricted(grTLD)
- test(tTLD)

#### gTLD
gTLD는 특별한 제한 없이 일반적으로 사용되는 최상위 도메인이며 세 글자 이상으로 구성된다.
초기 gTLD는 7개의 gTLD(.com, .edu .gov, .int, .mil, .net, .org)로 시작했으며 필요에 의해 새로운 gTLD가 만들어지고 있다.

#### Country Code (ccTLD)
cccTLD는 국가 최상위 도메인으로 규정된 두 글자의 국가 코드를 사용하며, 우리나라는 'kr'을 사용한다.
일반적으로 ccTLD를 사용하는 경우 Second Level TLD에는 gTLD에서 구분한 것처럼 사이트 용도에 따른 코드를 사용한다. 예를 들어 일반 회사는 co.kr을 사용하고 정부 기관은 go.kr을 사용하는 방법이다.

#### Sponsored
sTLD는 특정 목적을 위한 스폰서를 두고 있는 최상위 도메인으로, 스폰서는 특정 민족 공동체, 전문가 집단 등이 속할 수 있으며, 종류에는 '.aero', '.asia', '.edu' 등이 있다.

#### infrastructure
운용상 중요한 인프라 식별자 공간을 지원하기 위해 전용으로 사용되는 최상위 도메인이다.

#### Generic-restricted
grTLD는 특정 기준을 충족하는 사람이나 단체가 사용할 수 있는 최상위 도메인이다.

#### Test
tTLD는 IDN(International Domain Names) 개발 프로세스에서 테스트 목적으로 사용하는 최상위 도메인이다.

#### DNS 동작 방식
도메인을 IP 주소로 변환하려면 DNS 서버에 도메인 쿼리하는 과정을 거쳐야 한다.
하지만 DNS 서버 없이 로컬에 도메인과 IP 주소를 직접 설정해 사용할 수도 있다. 로컬에서 도메인과 IP 주소를 관리하는 파일을 hosts 파일이라고 한다. hosts 파일에 도메인과 IP 주소를 설정해두면 해당 도메인 리스트는 항상 DNS 캐시에 저장된다.

도메인을 쿼리하면 DNS 서버에 쿼리하기 전 로컬에 있는 DNS 캐시 정보를 먼저 확인한다.
동일한 도메인을 매번 질의하지 않고 성능을 향상시키기 위함이다. 이런 DNS 캐시 정보에는 기존 DNS 조회를 통해 확인한 동적 DNS 캐시와 함께 hosts 파일에 저장되어 있는 정적 DNS 캐시가 함께 저장되어 있다.
DNS 캐시 정보에 필요한 도메인 정보가 없으면 DNS 서버로 쿼리를 수행하고 DNS 서버로부터 응답을 받으면 그 결과를 캐시에 먼저 저장한다. 전에 쿼리를 수행한 DNS 정보는 캐시부터 조회하므로 DNS 서버에 별도로 쿼리하지 않고 캐시 정보를 사용한다.

다음 그림은 캐시와 DNS를 이용해 도메인 이름 쿼리를 하는 예제이다. 'zigispace.net'이라는 도메인을 쿼리하기 위해 먼저 로컬 캐시를 조회하고 캐시에 없다면 DNS 서버로 다시 쿼리한다.
