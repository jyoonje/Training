ApplicationContext를 스프링 컨테이너라 한다.

기존에는 개발자가 AppConfig 클래스를 호출해서 직접 객체를 생성하고 DI 했지만, 스프링 컨테이너가 이 역할을 대신해 줄 수 있다.

스프링 컨테이너는 @Configuration이 붙은 AppConfig를 설정(구성)정보로 사용한다. 여기서 @Bean이라 적힌 메서드를 모두 호출해서 반환된 객체를 스프링 컨테이너에 등록한다. 이렇게 스프링 컨테이너에 등록된 객체를 스프링 빈이라 한다.

스프링 빈은 @Bean이 붙은 메서드의 명을 스프링 빈의 이름으로 사용한다.



스프링 컨테이너가 생성되는 과정을 알아보자.

ApplicationContext applicaitonContext = new AnnotationConfigApplicationContext(AppConfig.class);





ApplicactionContext를 스프링 컨테이너라 한다.



ApplicationContext는 인터페이스이다.



스프링 컨테이너는 XML 기반으로 만들 수 있고, 어노테이션 기반의 자바 설정 클래스로 만들 수 있다.



스프링 컨테ㅐ이너의 생성 과정





new AnnotationConfigApplicationContext(AppConfig); 와 같이, 구현체에 설정 클래스를 매개변수로 넣어준다.



스프링 컨테이너가 실행되면 @Configuration 어노테ㅐㅐ이션이 붙은 파일을 탐색한다.



@Bean 어노테이션이 붙은 메서드를 스프링 컨테이너의 빈 저장소에 [빈 이름, 빈 객체](ex: [memberService, memberService@x011]) 형태로 저장한다.



스프링 빈 의존관계를 설정한다: 예를 들어, 스프링 빈 끼리 서로 의존관계가 있다면 이 단계에서 주입한다.

참고로 스프링 컨테이너는 스프링 빈을 생성하고, 의존관계를 주입하는 단계가 나누어져있다.

지금까지 과정을 정리하자면, 스프링 컨테이너를 생성하고 설정 정보를 참고해서 스프링 빈도 등록하고, 스프링 빈 간의 의존관계도 정의했다. 이제 컨테이너에서 빈 데이터(이름 등)를 조회할 수도 있다.


#### BeanFactory와 ApplicationContext
<img width="342" height="434" alt="image" src="https://github.com/user-attachments/assets/99e9329c-7d54-4207-8847-c8e4fd0544d2" />

- BeanFactory
  - 스프링 ㅋ컨테이너의 최상위 인터페이스이다.
  - 스프링 빈을 ㄱ관리하고 조회하는 역할을 담당한다.
  - getBean()을 제공한다.
- ApplicationContext
  - BeanFactory 기능을 모두 상속받아서 제공한다.
  - 빈을 관리하고 검색하는 기능을 BeanFactory가 제공해주는데, 둘의 차이는 뭘까
  - 애플리케이션을 개발할 때는 빈을 관리하고 조회하는 기능은 물론이고, 수많은 부가 기능이 필요하다.
 
**ApplicationContext가 제공하는 부가 기능**
<img width="730" height="282" alt="image" src="https://github.com/user-attachments/assets/64e7c216-71f2-4ace-b499-e45b69209d4b" />

- 메시지 소스를 활용한 국제화 기능
  - 한국에서 들어오면 한국어로, 영어권에서 들어오면 영어로  출력
- 환경 변수
  - 로컬, 개발, 운영 등을 구분해서 처리
- 애플리케이션 이벤트
  - 이벤트를 발행하고 구독하는 모델을 편리하게 지원
- 편리한 리소스 조회
  - 파일, 클래스 패스, 외부 등에서 리소스를 편리하게 조회

정리
- ApplicationContext는 BeanFactory의 기능을 상속받는다.
- 빈 관리 기능 + 부가 기능을 제공한다.
- BeanFactory를 직접 사용할 일은 거의 없다. 부가 기능이 포함된 ApplicaitionContext를 사용한다.
- BeanFactory나 ApplicationContext를 스프링 컨테이너라 한다.


빈 설정 정보 파일(예를 들면 AppConfig.class)은 어노테이션 기반의 Java 코드로만 구현 가능한 것이 아니라, xml 기반도 가능하다.
스프링 컨테이너는 ApplicaionContext와 AppConfig의 관계 또한 느슨하게 의존하도록 구성되어있다. 무슨 말이냐면, ApplicationCOntext는 AppConfig가 무슨 형태로 구현되었는지 신경쓰지 않는다 BeanDefinition이 있기 때문이다.

스프링 빈 설정 메타 정보 - BeanDefinition
-  @Component 같은 어노테이션을 스프링  컨테이너가 발견하면, "이 빈을 만들어야겠다" 정도가 아니라, 이 빈을 어떻게 만들고 관리해야 하는지에 ㄷ ㅐ한 메타데이터를 등록해둔다.
- 스프링은 어떻게 다양한 설정 정보(xml, java)를 지원하는 것일까? 그 중심에는 BeanDefinition 이라는 ㅊ추상화가 있다.
- xml을 읽든, Java 코드를 읽든 BeanDefinition을 만든다. 스프링 컨테이너는  어떤 형태로 구현되었든 신경쓰지 않고, BeanDefinition만 의존하면 된다.
- BeanDefinition을 빈 설정 메타정보 라고 한다.
  - @Bean, <Bean>당 각각 ㅎ ㅏ나씩 메타 정보가 생성된다.
- 스프링 컨테이너는 이 메타정보를 기반으로 스프링 빈을 생성한다.

#### 웹 애플리케이션과 싱글톤
- 스프링은 태생이 기업용 온라인 서비스 기술을 지원하기 위해 탄생했다.
- 웹 애플리케이션은 보통 많은 고객이 동시에 요청을 보낸다.

이전에 우리가 만들었던 순수 자바 기반의 DI컨테이인 AppConfig는 요청을 보낼 때 마다 새로운 memberService 객체를 생성한다.
이는 요청이 많아질 수록 새로운 객체가 메모리 공간을 차지하며, 리소스 낭비가 심하다.

#### 싱글톤 패턴
- 클래스의 인스턴스가 1개만 생성되는 것을 보장하는 디자인 패턴
- 객체 인스턴스를 2개 이상 생성하지 못함
  - private 생성자를 사용해서 외부에서 임의로 new 키워드를 사용하지 못하게 막아야 함
 
순수 자바 코드로 싱글톤 패턴을 구현하는 방법은, public class에 private static final 키워드로 자기 자신의 객체를 1개만 생성한다.
그리고, public static getInstance() 메서드를 만들어서, private static final 멤버를 반환하는 이 클래스의 유일한 public 접근 제어자 getter를 만든다.
생성자를 private으로 선언해서, 다른 클래스에서 이 클래스의 생성자를 호출해서 new 키워드를 사용한 객체 생성을 못하도록 한다.

이렇게 클래스를 구현하면, 
A a1 = A.getInstance();
A a2 = A.getInstance();

sout(a1);, sout(a2);  // 같은 참조값을 가진 객체이다.

싱글톤 패턴을 적용하면 사용자의 요청이 들어올 때 마다 객체를 생성하는 것이 아니라,, 이미 만들어진 객체를 공유해서 효율적으로 사용할 수 있다.
하지만 싱글톤 패턴은 다음과 같은 문제점을 갖고있다.
- 싱글톤 패턴을 구현하는 코드 자체가 많이 들어간다.
- getInstance() 메서드를 직접 호출해야 하기 떄문에, 클라이언트가 구체 클래스에 의존한다.
