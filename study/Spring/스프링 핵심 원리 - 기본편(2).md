관심사의 분리

스프링 컨테이너를 사용하지 않던 기존 자바 코드:


public interface Animal;

public class Dog implements animal;

public class Cat implements animal;




class A {

// Animal animal = new Dog;

Animal animal = new Cat; // Cat으로 변경

}




와 같이, 구현체를 직접 넣어줘야 했기 때문에 완전한 DIP 적용에 실패했음.

AppConfig를 통해 관심사를 분리하자.




public interface Animal;

public class Dog implements animal;

public class Cat implements animal;




class AppConfig {

public Animal animal{

return new Cat();

}

}

class A {

AppConfig appConig = new AppConfig();

Animal animal = appConfig.animal();

}




--> 클래스 A의 코드를 변경하지 않고, 인터페이스(현재는 인터페이스가 아니지만, 기능적으로 인터페이스 역할을 하는) AppConfig를 통해 구현체를 dog에서 cat으로 변경했다.




이후에 cat에서 다시 dog로 바뀌든, 다른 구현체가 등장하든 구현체를 사용하는 주체인 클래스A는 수정되지 않는다. DIP 적용의 예시를 들어봤다.



제어의 역전(IoC):

위의 코드로 IoC를 설명하자면, 기존의 순수 자바 코드는 호출 객체가 구현 객체를 임명해줘야했다. 반면 AppConfig가 등장한 이후부터 호출 객체는 자신의 로직을 실행하는 역할만 하며, 어떤 Animal 객체가 생성될 지 알 수 없다. 프로그램에 대한 제어 흐름의 권한은 모두 AppConfig가 가지고 있다. 이렇듯 프로그램의 제어 흐름을 호출 객체가 제어하는 것이 아니라 외부에서 관리하는 것을 제어의 역전(IoC)라고 한다.




의존 관계 주입(DI):

클래스A는 Animal 인터페이스에 의존한다. 실제 어떤 구현 객체가 사용될 지는 모른다.

의존 관계는 "정적인 클래스 의존 관계와, 실행 시점에 결정되는 동적인 객체(인스턴스) 의존 관계 두 개를 분리해서 생각해야 한다.




하지만 여기서,

DI를 적용한 뒤 신규 개발자가 클라이언트 코드만 봐서는 실제 구현체가 무엇인지 알기 어려워진다.

그래서 Spring은 의존성 주입 자체뿐만 아니라, "어떤 구현체가 주입되는가"를 개발자가 추적할 수 있도록 여러 장치를 제공한다.




차후 스프링 컨테이너의 동작 과정을 이해하게 되면 위의 의구심은 해소될 테지만, 개발자가 실제로 어떻게 코드를 분석하는지 미리 요약하자면 다음과 같다.

① A가 무엇을 의존하는가?

↓

② 그 타입의 구현체가 무엇인가?

↓

③ 구현체가 Spring Bean인가?

↓

④ Bean이 어떻게 등록되는가?

↓

⑤ 여러 구현체가 있다면 @Primary / @Qualifier가 있는가?

↓

⑥ @Bean 메서드로 직접 등록되는 것은 아닌가?

↓

⑦ @Profile / @Conditional 등이 적용되는가?

↓

⑧ 실제 실행 시 어떤 Bean이 선택되는가?









위의 과정들을 파고들다보면, 자연스럽게

@Component

↓

Component Scan

↓

BeanDefinition

↓

ApplicationContext

↓

Bean 생성

↓

Dependency Injection

↓

Reflection

↓

Proxy

로 이어진다. 그리고 이것은 Java심화 -> JVM -> Spring 내부 구조와 정확하게 연결되니, 끝까지 공부하자
