웹 애플리케이션과 싱글톤

스프링은 태생이 기업용 온라인 서비스 기술을 지원하기 위해 탄생했다.

웹 애플리케이션은 보통 많은 고객이 동시에 요청한다.

우리가 과거에 만들었던 순수한 DI컨테이너인 AppConfig는 요청이 들어올 때마다 새로운 객체(MemeberService)를 생성한다. 트래픽이 많이 발생할 수록 메모리 낭비가 심해지며, 이 대한으로 객체가 딱 1개면 생성되고 공유하도록 설계된 싱글톤 패턴이 사용된다.



싱글톤 패턴

클래스의 인스턴스가 딱 1개만 생성되는 것을 보장하는 디자인 패턴이다.

객체 인스턴스를 2개 이상 생성하지 못하도록 막아야 한다 - private 생성자를 사용해서, 외부에서 임의로 new 키워드를 사용하지 못하도록 막아야 한다.

예시(수도 코드)





SingToneService 클래스 생성



private static final SingTone instance 필드 생성



public static SingleToneService getInstance() 메서드 생성 (retirn instance)



생성자를 private 접근제어자로 생성
private SingletonService SingletonService();


static 영역에 객체 instance를 미리 생성 후, 이 객체 인스턴스가 필요하면 오직 getInstance() 메서드를 통해서만 조회 가능하다. 생성자를 private로 막아두었기 떄문에, new 키워드로 객체 인스터스가 추가 생성되는 것을 막는다.


싱글톤 패턴의 문제점





싱글톤 패턴을 구현하는 코드 자체가 길어진다



의존 관계상 클라이언트 코드가 구체 클래스에 의존한다. -> getInstance() 와 같은 구현체의 생성/획득 방법까지 알아야 하기 때문이다.



내부 속성을 변경하거나 초기화 하기 어렵다.



private 생성자로 자식 클래스를 만들기 어렵다.

싱글톤 컨테이너

스프링 컨테이너는 싱글톤 패턴의 문제를 해결하면서, 객체 인스턴스를 싱글톤으로 관리한다.

스프링 컨테이너는 싱글톤 컨테이너 역할을 한다. 이렇게 싱글톤 객체를 생성하고 관리하는 기능을 싱글톤 레지스트리라 한다.





싱글톤 패턴을 위한 보일러 플레이트 코드가 들어가지 않아도 된다.



DIP, OCP,private 생성자로부터 자유롭게 싱글톤 패턴을 사용할 수 있다.

스프링의 기본 빈 등록 방식은 싱글톤이지만, 요청할 때마다 새로운 객체를 생성해서 반환하는 기능도 제공한다. 필요에 따라 해당 기능을 사용할 수 있다.



싱글톤 방식의 주의점

싱글톤 패턴이든, 싱글톤 컨테이너를 사용하든 간에, 싱글톤 객체는 상태를 유지(stateful)하게 설계하면 안된다.

특정 클라이언트에 의존적인 필드가 있으면 안된다.

특정 클라가 값을 변경할 수 있으면 안되며, 가급적 읽기만 가능해야한다. 필드 대신에 자바에서 공유되지 않는 지역변수, 파라미터, ThreadLocal 등을 사용해야 한다.

항상 스프링 빈은 무상태로 설계하자. 공유되는 빈(ex: memberService)는 무상태로 설계하고, 메서드 내 지역변수와 같은 값은 각 호출마다 독립적으로 생성되기 때문에(즉 싱글톤으로 관리하지 않기 때문에) 상태를 변경해도 괜찮다.



@Configuration과 싱글톤

AppConfig 클래스를 다시 보자

public class AppConfig{

    @Bean 
    public MemberService memberService() {
return new MemberServiceImpl(memberRepository());
}

@Bean publci OrderService orderService(){
return new OrderserviceImpl(memberRepository(), discountPolicy());
}

@Bean
public MemberRepository memberRepository() {
return new MemoryMemberRepository();
}

만약 Appconfig 외부의 클래스에서,
MemberService memberService = new MemberService();
OrderService orderService = new OrderService();
와 같이 memberService, orderService 객체를 생성하게 되면, memberRepository 생성자가 두 번 호출되면서 memoryMemeberReposotry 생성자도 두 번, 객체도 두 번 생성되게 된다.

싱글톤이 깨지는 것처럼 보이는데, memberRepository 객체를 조회하면 어떻게 되고 있을까?



분명 new 키워드를 사용하여 memberRopository 객체가 여러번 호출되었음에도, 조회 결과 모두 같은 인스턴스가 공유되어 사용되고있다.


스프링 컨테이너는 싱글톤 레지스트리이다. 따라서 스프링 빈이 싱글톤이 되도록 보장해주어야 한다. 하지만 스프링 컨테이너가 자바 코드까지 통제하기에는 어렵다. 따라서 자바 코드를 본다면 분명히 new 키워드가 여러번 호출되어야 하는 것이다.

그래서 스프링은 클래스의 바이트코드를 조작하는 라이브러리를 사용한다. 모든 비밀은 @Configuration을 적용한 AppConfig에 있다.

@Configuration 어노테이션이 붙은 클래스인 AppConfig 자체의 빈을 조회해서 빈의 클래스를 출력해보면, 다음과 같이 되어있다.

'app.core.AppConfig.xxxCGLIB'

AppConfigxxCGLIB이라는 클래스가 되어서 빈으로 등록되는 것을 볼 수 있다. 해당 클래스는 AppConfig를 상속받으며, 실제 빈 인스턴스는 상속받은 클래스인 AppConfig@CGLIB으로 등록된다. 해당 클래스는 AppConfig를 완벽하게 상속받아서 오버라이딩한다. 다음과 같이 바이트코드를 조작해서 작성되어있을 것이다.

@Bean
public class AppConfig{
@Bean public MemberRepository memberRepository{

if(memoryMemberRepository가 이미 컨테이너에 등록되어있다면){
return 생성되어있던 기존 빈 반환
}
}
else {
MemoryMemberRepository를 생성하고 스프링 컨테이너에 등록
return 새로운 빈
}
}
}

@Bean 이 붙은 메서드마다 이미 스프링 빈이 존재하면 존재하는 빈을 반환하고, 스프링 빈이 없으면 생성해서 스프링 빈으로 등록 후 반환한다. 이런 방식으로 싱글톤 스코프를 보장한다.



그렇다면 @Configuration을 사용하지 않고 @Bean만 적용하면 어떻게 될까?

@Configuration을 사용하면 바이트코드를 조작하면 CGLIB 클래스로 만들지만, 만약 사용하지 않는다면 싱글톤을 보장할까?

클래스에 @Confi..를 붙이면, 각 메서드들은 빈으로 등록되지만, AppConfigCGLIB 클래스 하위의 메서드로 생성되지 않기 때문에 싱글톤을 보장하지 않는다. memberRepository 객체가 new키워드를 통해 여러번 호출되어 화면에 출력된다.

@Bean 키워드로 빈을 등록한다해서 스프링 컨테이너가 new 키워드로 생성한 자바 코드까지 핸들링하지는 못한다. 다만, @Configuration 어노테이션이 붙은 클래스 내부에 있다면 얘기가 달라진다. 해당 객체에 대한 싱글톤 보장이 가능해지는 것이다.

@Bean

"이 메서드가 반환하는 객체를 Bean으로 등록해라"

"컨테이너가 관리하는 Bean을 필요한 곳에 주입해라."




컴포넌트 스캔

컴포넌트 스캔과 의존관계 자동 주입 시작하기

지금까지 스프링 빈을 등록할 때는 @Bean을 통해 설정 정보에 직접 스프링 빈을 나열했다.

이렇게 등록해야 할 빈이 많아지면 귀찮고, 누락하는 문제가 생긴다.

그래서 설정 정보가 없이도 자동으로 스프링 빈을 등록하는 컴포넌트 스캔이라는 기능을 제공한다.

컴포넌트 스캔을 사용하려면 먼저 @ComponenetScan을 설정 정보에 붙여주면 된다. 컴포넌트 스캔은 이름 그대로 @Component 어노테이션이 붙은 클래스를 스캔해서 스프링 빈으로 등록한다. 즉 @Confuguration 설정 클래스에서 처럼 각 메서드의 빈 생성 방법을 정의하고, @Bean 어노테이션을 붙일 필요가 없다. 이렇게 보면 @Configuration 설정 파일은 쓸 일이 없어보이지만, 써드 파티 라이브러리를 import해서 의존성을 부여할 때와 같이 특수한 의존성을 개발자가 직접 부여해야 할 때는, ComponenetScan과 같이 스프링에 전적으로 역할을 부여하게 되면 시각적으로도 알아보기 힘들고, 스프링 컨테이너가 어떠한 빈을 의존성으로 부여해야 할 지 찾지 못하는 경우가 생길 수 있기 때문에 @Configuration을 사용하곤 한다.

ComponectScan은 빈 생성을 자동으로 해주지만, 필요한 의존관계까지 주입해주진 않는다. 따라서, Component로 등록된 각 클래스의 생성자에 @Autowired 어노테이션을 붙여주면 스프링 컨테이너가 생성자를 보고, 필요한 타입의 빈을 조회해서 의존 관계를 주입해준다.

컴포넌트스캔의 탐색 위치와 기본 스캔 대상

어노테이션의 첫 번째 인자로 basePackage를 지정할 수 있으며, 지정된 패키지 하위의 클래스를 탐색한 뒤 컴포넌트로 등록한다. 만약 베이스 패키지를 지정하지 않는다면, 기본적으로 @ComponenetScan이 붙은 설정 정보 클래스의 패키지가 탐색 시작 위치가 된다. 따라서 프로젝트 메인 설정 정보는 프로젝트를 대표하는 정보이기 때문에 프로젝트 시작 루트 위치에 지정하고, basePackge를 생략하는 것이 일반적이다.

컴포넌트 스캔 기본 대상

@Component 뿐만 아니라

@Controller, @Service, @Repository, @Configuration도 추가로 스캔 대상에 포함한다.

컴포넌트 스캔의 용도 뿐만 아니라 다음 어노테이션이 있으면 스프링은 부가 기능을 수행한다.

@Controller: 스프링 MVC 컨트롤러로 인식

@Repository: 스프링 데이터 접근 계층으로 인식, 데이터 계층의 예외를 스프링 예외로 변환해준다.

@Configuration: 스프링 설정 정보로 인식, 스프링 빈이 싱글톤을 유지하도록 추가 처리를 한다.

@Service: 특별한 처리를 하지 않는다. 대신 개발자들이 '핵심 비즈니스 로직이 여기 있겠구나'하고 비즈니스 계층을 인식하는데 도움을 준다.

@ComponenetScan 과 @Bean의 차이점

1. @Bean
- @Bean은 메서드가 반환하는 객체를 Spring Bean으로 등록하며, 개발자가 객체를 어떻게 생성하고 어떤 의존관계를 사용할지 직접 명시할 수 있다. 따라서 객체 생성 방법을 세밀하게 제어할 수 있지만, 직접 설정해야 하는 코드가 늘어날 수 있다.

2. @ComponentScan
- @ComponentScan은 지정된 패키지를 탐색하여 @Component, @Service, @Repository 등의 어노테이션이 붙은 클래스를 찾아 Bean으로 자동 등록한다.
- 등록된 Bean들의 의존관계 역시 스프링 컨테이너가 관리하며, 생성자 주입 등을 통해 의존성을 주입한다.
