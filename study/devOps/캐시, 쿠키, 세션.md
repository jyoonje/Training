캐시: 다시 받을 필요가 없도록 데이터를 저장
쿠키: 서버가 클라이언트를 식별하거나 상태를 전달하기 위해 브라우저에 저장하는 작은 데이터
세션: 서버가 클라이언트의 상태를 서버 측에 저장하고 식별하는 방식


---

#### 1. 캐시
**캐시는 이미 받은 데이터를 나중에 재사용하기 위해 저장해 두는 것**이다.
예를 들어 웹사이트에 처음 접속했다고 해보자.

```
브라우저                         서버
   │                              │
   │── GET /index.html ──────────>│
   │                              │
   │<──── index.html ─────────────│
   │                              │
   │── GET /style.css ───────────>│
   │                              │
   │<──── style.css ──────────────│
```

이 때 브라우저는 받은 index.html, style.css, JS 파일, 이미지 등을 캐시에 저장할 수 있다.
그리고 다시 같은 사이트에 접속하면:
```
브라우저 캐시
    │
    ├── index.html
    ├── style.css
    ├── app.js
    └── logo.png
```

서버에 매번 다시 요청하지 않고 캐시에 있는 파일을 사용할 수 있다.
따라서 속도와 네트워크 사용량을 개선할 수 있다.

#### 1-1. 캐시는 누구의 캐시인가?
캐시는 브라우저에만 존재하는 개념이 아니다.
여러 위치에 캐시가 존재할 수 있다.
```
사용자 브라우저
      ↓
브라우저 캐시

      ↓

프록시 / CDN
      ↓
CDN 캐시

      ↓

서버
      ↓
서버 내부 캐시
```

즉 캐시는 특정 기술 하나가 아니라, "재사용을 위해 데이터를 저장하는 매커니즘"이라고 이해하는게 좋다.

---

#### 쿠키

쿠키는 캐시와 목적이 완전히 다르다.
쿠키는 기본적으로 **웹 브라우저가 갖고 있는 작은 데이터**이다.
예를 들어 서버가 브라우저에게 다음과 같이 응답할 수 있다.
```
HTTP/1.1 200 OK
Set-Cookie: userId=1234
```

브라우저는 이것을 저장한다.
```
브라우저
┌──────────────────────┐
│ Cookie               │
│                      │
│ userId = 1234        │
└──────────────────────┘
```

그리고 이후 해당 조건에 맞는 요청을 서버에 보낼 때, 
```
GET /mypage HTTP/1.1
Cookie: userId=1234
```
처럼 쿠키를 함께 보낼 수 있다.
즉, 서버 -> Set Cookie -> 브라우저 -> Get Cookie -> 서버에 요청 시 Cookie를 제시
라는 흐름이 만들어진다.

#### 3. 쿠키는 왜 필요한가
HTTP의 중요한 특징 중 하나가 Stateless 하다는 것이다.
예를 들어 서버에 요청을 보낸다고 하자.
```
GET /mypage
```
서버 입장에서는 이 요청을 보고 "이 사람이 누구지?"를 반드시 알 수 있는 것은 아니다.
HTTP 요청 자체에는 기본적으로 "이전 요청을 보낸 그 사람"이라는 정보가 없기 때문이다.
그래서 쿠키를 사용할 수 있다.
```
브라우저                  서버

POST /login
아이디 / 비밀번호 ────────>

                     로그인 성공
                     Set-Cookie:
                     sessionId=ABC123
                         │
                         ↓
<────────────────────────┘

브라우저:
sessionId=ABC123 저장
```

그 이후의 다음 요청부터
```
GET /mypage
Cookie: sessionId=ABC123
```
와 같이 요청을 보내면 서버는 요청자를 식별 가능해진다.

#### 4. 세션
세션은 쉽게 말하면 **서버가 클라이언트의 상태를 일정 기간 동안 유지하기 위한 공간**이다.
예를 들어 로그인하면 서버가,
```
Session 저장소

ABC123
  ↓
userId = 100
login = true
```
라는 정보를 저장할 수 있다.
그리고 브라우저에서는, 
```
sessionId = ABC123
```
만 쿠키로 저장할 수 있다.
그러면 전체 구조는, 
```
             브라우저
        ┌─────────────────┐
        │ Cookie          │
        │ sessionId=ABC123│
        └────────┬────────┘
                 │
                 │ HTTP Request
                 │ Cookie: sessionId=ABC123
                 ↓
             서버
        ┌─────────────────┐
        │ Session 저장소  │
        │                 │
        │ ABC123          │
        │   ↓             │
        │ userId = 100    │
        │ login = true    │
        └─────────────────┘
```

위의 그림이 세션 기반 로그인의 대표적인 구조이다.

#### 5. 그러면 쿠키와 세션은 서로 반대인가?
아니다. 쿠키와 세션은 경쟁 관계가 아니라, 오히려 같이 사용하는 경우가 많다.
사용자가 로그인 시 서버는 세션을 생성해서 브라우저에 쿠키를 할당해주고,
이후 Session 저장소에서 쿠키를 기반으로 사용자를 식별한다. 즉, 쿠키는 세션을 식별하기 위한 ID를 브라우저에 저장하는 용도이다.

#### 6. "세션은 서버에 저장된다"의 의미

세션이라는 것은 서버 측에 상태를 저장하는 개념이고, 실제 저장 장소를 메모리, Redis, DB, 파일 등 여러 곳이 될 수 있다.


#### 7. 세션의 생명주기
세션에는 보통 일정한 생명주기가 있다.
```
로그인
 ↓
세션 생성
 ↓
사용자가 요청
 ↓
세션 사용
 ↓
일정 시간 동안 활동 없음
 ↓
세션 만료
```
또는 로그아웃 시, 서버에서 세션 삭제/무효화가 진행되곤 한다.
그래서 세션에는 보통 세션 타임아웃 이라는 개념이 존재한다.

일반적으로 Chrome 개발자 도구에서 브라우저가 저장 중인 쿠키/세션을 볼 수 있다.
개발자 도구에서, **Application -> Storage -> Cookies**로 들어가면 현재 사이트의 쿠키를 볼 수 있다.

캐시는 쿠키처럼 단순히
`Application -> Cache`에서 모든 캐시 파일을 볼 수는 없다. 실제로 캐시 동작을 확인하려면 Network 탭이 더 중요하다.
개발자 도구의 `Network -> 요청 선택 -> Headers`에서 응답 헤더를 확인할 수 있다.
예를 들어,
```
Cache-Control: max-age=3600
ETag: "abc123"
```
그리고 요청을 다시 보낼 때 캐시가 사용되었는지 Network 탭에서 확인할 수 있다.

또한 크롭 브라우저에서는 `Application -> Cache Storage`에서 웹 애플리케이션이 사용하는 Cach Storage API의 캐시를 볼 수 있지만, 이것이 HTTP 브라우저 캐시와 동일한 개념은 아니다.

즉 그림으로 요약하자면 다음과 같다.
```
Application
 ├─ Storage
 │   └─ Cookies       ← 쿠키
 │
 └─ Cache Storage    ← Cache Storage API

Network
 └─ Headers          ← HTTP 캐시 관련 헤더/동작 확인
```
